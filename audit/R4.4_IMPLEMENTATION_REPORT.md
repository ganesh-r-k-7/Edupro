# R4.4 Enrollment Prediction API Implementation Report

## Architecture Overview

The EduPro Enrollment Prediction API is a FastAPI-based REST service that exposes the existing enrollment prediction functionality to external applications. The API reuses the canonical feature engineering, validation, and prediction pipeline from the `edup.features` and `edup.models` modules, ensuring full parity with the Streamlit dashboard.

### Key Design Decisions

1. **Reuse over Rewrite**: The API does not implement separate prediction logic. It imports and uses `edup.features.validate_course_inputs`, `edup.features.build_feature_frame`, and the model's `predict()` method directly.

2. **Registry-First Model Loading**: The API loads models from the Model Registry (introduced in R4.5 prep work) with fallback to `enrollment_model_phase1.pkl`. The legacy `enrollment_model.pkl` is explicitly excluded because it uses a different (transaction-level) feature contract incompatible with the current course-level feature engineering.

3. **Single-Load Lifecycle**: Models are loaded once per API process via FastAPI's lifespan handler, cached in module-level globals, and reused across all requests.

4. **Structured Error Handling**: Consistent JSON error responses with appropriate HTTP status codes (400, 422, 500, 503) without exposing stack traces or filesystem paths.

5. **Comprehensive Documentation**: Auto-generated Swagger UI (`/docs`), ReDoc (`/redoc`), and OpenAPI JSON (`/openapi.json`).

## Endpoint Contracts

### GET /health
- **Purpose**: Health check with model availability status
- **Response**: `{status, model_available, model_name?, model_version?}`
- **Status**: `healthy` (model loaded) or `degraded` (no compatible model)
- **Behavior**: Does not reload model; returns cached state

### GET /model-info
- **Purpose**: Safe model metadata for clients
- **Response**: Full model metadata including features, metrics, training date, registry version
- **Security**: No filesystem paths, secrets, or sensitive internals exposed
- **Error**: 503 if model unavailable

### POST /predict/enrollment
- **Purpose**: Enrollment prediction for course configurations
- **Request**: Canonical feature contract (6 required + 3 optional fields)
- **Validation**: Enum checks, numeric bounds, Free/Paid price normalization
- **Response**: `{predicted_enrollment, model_name?, model_version?, features_used}`
- **Errors**: 400 (value validation), 422 (schema validation), 503 (model unavailable), 500 (internal error)

### GET /model-registry
- **Purpose**: List all registered model versions
- **Response**: Array of version metadata (newest first)

### GET /model-registry/{version}
- **Purpose**: Get specific version details
- **Response**: Full registry entry metadata
- **Error**: 404 if version not found

## Model Lifecycle Strategy

| Scenario | Behavior |
|----------|----------|
| Registry active model exists | Load from registry, build metadata from registry entry |
| No registry model, Phase 1 model exists | Load `enrollment_model_phase1.pkl` with metadata |
| No compatible model | Return 503 on `/model-info` and `/predict`; health shows `degraded` |
| Corrupted model artifact | Log error, set load error state, return 503 |

The legacy `enrollment_model.pkl` is **not** used as fallback because its feature contract (including PaymentMethod, TransactionMonth, Quarter, IsWeekend, SeasonalityLabel, ExpertiseCategoryMatch) is incompatible with the current course-level feature engineering pipeline.

## Security Considerations

- **Local by Default**: API binds to configurable host/port; no public exposure
- **No Authentication**: Not implemented (no documented requirement)
- **No Secrets Exposed**: Error responses sanitize filesystem paths and internal details
- **Input Validation**: Strict enum and bounds checking on all prediction inputs
- **Structured Logging**: Exceptions logged server-side with full context; clients receive generic messages

## Known Limitations

1. **Model Quality**: The enrollment model does not beat a mean baseline on this dataset (CV RMSE 13.05 vs baseline 12.27). Predictions reflect the legacy artifact unless Phase 1 model is trained.

2. **No Auth/Rate Limiting**: Prototype API; production hardening would require authentication, rate limiting, and HTTPS termination.

3. **Registry Dependency**: Registry endpoints require the Model Registry (R4.5 prep work). If registry unavailable, core endpoints still function with Phase 1 fallback.

4. **Legacy Model Excluded**: `enrollment_model.pkl` cannot be used due to feature contract mismatch. This is intentional.
