## 5. Error Handling

### 5.1 Exception Taxonomy (Verified)

| Exception | Inherits From | Use Case |
|-----------|---------------|----------|
| `DataContractError` | `ValueError` | Schema/contract violations |
| `DataUnavailableError` | `DataContractError` | Missing/corrupt data files |
| `ModelLoadError` | `Exception` | Failed model artifact loading |
| `ForecastError` | `DataContractError` | Forecast payload/validation failures |
| `DashboardError` | `Exception` | Dashboard initialization failures |

### 5.2 Error Handling Improvements

- **Exception chaining preserved**: All `raise ... from exc` patterns maintained
- **No broad `except Exception`**: Only specific catches (e.g., `except (pd.errors.ParserError, ValueError, OSError)`)
- **User-facing messages**: Errors include actionable guidance (e.g., "Run the preprocessing and feature-engineering steps")
- **No internal secrets/stack traces exposed**: Messages are descriptive but not verbose
- **Proper abstraction level**: Data errors raised in `data.py`, model errors in `models.py`, etc.
